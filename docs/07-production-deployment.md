# چک‌لیست استقرار Production

این سند برای استقرار واقعی روی هاست نوشته شده است. مقادیر محرمانه فقط در `.env` سرور قرار می‌گیرند و نباید داخل Git یا این سند نوشته شوند.

## قبل از انتشار

- PHP 8.2+، MariaDB/MySQL، افزونه‌های `mbstring`، `openssl`، `pdo_mysql`، `fileinfo`، `curl`، `zip` و `SimpleXML` فعال باشند.
- `APP_ENV=production`، `APP_DEBUG=false` و `APP_URL` با دامنه واقعی تنظیم شوند.
- `APP_KEY` یکتا روی سرور تولید شود؛ کلید سرور دیگری کپی نشود.
- `DB_*` با دیتابیس Production تنظیم شود؛ دیتابیس Preview یا SQLite داخل `.freebuff` هرگز منتقل نشود.
- `CACHE_STORE=redis`، `QUEUE_CONNECTION=redis` و `SESSION_DRIVER=database` یا Redis تنظیم شوند.
- اگر `AdminUserSeeder` در Production اجرا می‌شود، قبل از seed مقدار قوی `SEED_ADMIN_PASSWORD` در `.env` قرار گیرد. مقدار پیش‌فرض توسعه (`password`) برای Production قابل استفاده نیست.
- `FILESYSTEM_DISK=local` یا دیسک private/S3-compatible برای فایل‌های پولی تنظیم شود؛ `ALLOW_LEGACY_PUBLIC_DOWNLOADS=false` بماند و فایل‌های دیجیتال داخل `storage/app/private` قرار بگیرند.
- `COMMERCE_RESERVATION_MINUTES` زمان نگهداری موجودی سبد را تعیین می‌کند (پیش‌فرض ۳۰ دقیقه).
- سرویس پیامک و درگاه فقط بعد از واردکردن کلیدهای واقعی فعال شوند: کلیدهای پیامک در `/admin/settings/sms`، درگاه پرداخت در `/admin/settings/payments` و بقیه اتصالات (ایتا و پیگیری‌های خودکار) در `/admin/settings/automations`.
- در اتومارکتینگ می‌توانید CSV یا XLSX با ستون‌های `موبایل`، `نام` و `ایمیل` وارد کنید؛ حجم فایل حداکثر ۱۰MB و تعداد ردیف حداکثر ۱۰٬۰۰۰ است. قبل از فعال‌کردن اجرای فوری، درایور پیامک را روی Log/Sandbox تست کنید.

## دیپلوی خودکار (deploy.sh)

اسکریپت `deploy.sh` فقط چیزهایی را که برای انتشار لازم است به سرور می‌برد: `public/build` (باندل جدید)، `public/sw.js`، فایل‌های `public/install*.php` و فایل‌های PHP تغییرکرده (با مقایسه زمان با marker محلی `.deploy-last`). دو روش انتقال دارد:

- **SSH** (پیشنهادی): با `scp` آپلود و بعد از آن `php artisan optimize:clear && config:cache && route:cache && view:cache` را روی سرور اجرا می‌کند (`--migrate` هم migration را اجرا می‌کند).
- **FTP** (هاست اشتراکی بدون SSH): با `curl --ftp-create-dirs` فایل‌ها را می‌فرستد و در پایان مسیر فایل‌های کش را برای حذف دستی نشان می‌دهد (`bootstrap/cache/config.php` و `routes-*.php` و `views-*.php`).

راه‌اندازی: تنظیمات را در `.deploy-config.local.sh` بگذارید (نمونه: `.deploy-config.example.sh` — این فایل در `.gitignore` است و هرگز داخل Git نمی‌رود).

```bash
cp .deploy-config.example.sh .deploy-config.local.sh   # و پر کردن مقادیر
bash deploy.sh --dry-run    # پیش‌نمایش فایل‌ها بدون آپلود
bash deploy.sh              # دیپلوی واقعی
bash deploy.sh --all        # آپلود کامل (اولین دیپلوی یا بازنشانی)
bash deploy.sh --migrate    # اجرای migrate بعد از آپلود (فقط SSH)
```

بعد از دیپلوی، یک `Ctrl+F5` در مرورگر کافی است؛ سرویس‌ورکر نسخه `v4` کش قدیمی باندل‌ها را خودش پاک می‌کند.

## نصب و Build

### روش پیشنهادی برای توسعه‌دهنده یا سروری که SSH دارد

```bash
composer install --no-dev --optimize-autoloader
npm ci
npm run build
php artisan storage:link # اختیاری؛ روی هاست‌های بدون symlink، fallback داخلی /storage فعال است
php artisan migrate --force
php artisan db:seed --class=RoleAndPermissionSeeder --force
php artisan db:seed --class=SiteSettingSeeder --force
php artisan db:seed --class=ContentSeeder --force
php artisan app:install --admin-name="مدیر سیستم" --admin-phone="09xxxxxxxxx" --admin-password="یک-رمز-حداقل-۱۰-کاراکتری"
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

### نصب آسان روی هاست اشتراکی بدون SSH

1. کل پروژه را آپلود کنید و Document Root دامنه را روی پوشه `public` قرار دهید؛ فایل‌های `vendor` و `public/build` باید از قبل همراه بسته باشند. اگر فقط فایل‌های نصب‌کننده را به‌روزرسانی می‌کنید، هر دو فایل `public/install.php` و `public/install-selfheal.php` را با هم آپلود کنید.
2. در صورت نبودن `.env`، فایل `.env.example` را کپی نکنید؛ آدرس `https://your-domain.example/install.php` را باز کنید تا Wizard آن را بسازد.
3. نوع دیتابیس، اطلاعات MySQL/MariaDB یا SQLite، نام سایت و حساب مدیر را وارد کنید. Wizard اتصال را تست می‌کند، کلید رمزنگاری را می‌سازد، migrationها و seedهای پایه را اجرا می‌کند و قفل نصب را در `storage/app/installed.lock` می‌سازد.
4. بعد از پایان، با شماره موبایل مدیر وارد شوید، سرویس پیامک و درگاه را از پنل تنظیم کنید و فایل `public/install.php` را حذف کنید. قفل نصب مانع اجرای دوباره است اما حذف فایل لایه دفاعی بهتری است.
5. Wizard تمام مراحل را **درون همان درخواست** و بدون فراخوانی Shell اجرا می‌کند (مناسب هاست‌هایی که `proc_open`/`exec` غیرفعال دارند): migrationها، seedهای پایه و ساخت مدیر اصلی. رمزها در این سند یا Git ذخیره نمی‌شوند.

#### عیب‌یابی نصب

- **SQLite:** اگر خطای «پوشه vendor موجود نیست» دیدید، ابتدا `composer install` را روی هاست اجرا کنید و دوباره نصب را شروع کنید. اگر خطای «قابل نوشتن نیست» دیدید، مجوز پوشه `database/` یا `storage/` را روی ۶۶۴/۷۷۵ تنظیم کنید.
- **MySQL/MariaDB:** اگر «اتصال MySQL برقرار نشد» با جزئیات `Access denied` دیدید، نام کاربری یا رمز دیتابیس اشتباه است. اگر `Unknown database` بود، نام دیتابیس را اشتباه وارد کرده‌اید (در cPanel معمولاً پیشوند دارد، مثلاً `user_db`). اگر `Connection refused` بود، Host را از `127.0.0.1` به `localhost` تغییر دهید یا پورت درست را از هاست بگیرید. Wizard به‌صورت خودکار `localhost` را هم امتحان می‌کند اما اگر هاست پورت/سوکت متفاوتی دارد، باید آن را در فرم وارد کنید.
- **خطای `1170 BLOB/TEXT column 'endpoint' used in key specification`:** این خطا یعنی روی هاست هنوز نسخه قدیمی فایل `database/migrations/2026_08_10_000430_add_production_foundations.php` هست که روی ستون TEXT ایندکس یکتا می‌سازد (MySQL/MariaDB این را رد می‌کند؛ در SQLite محلی دیده نمی‌شود). نصب‌کننده خودش این را تشخیص می‌دهد و فایل‌های قدیمی را با نسخه درست بازنویسی می‌کند (نسخه قبلی با پسوند `.bak` کنارش نگه داشته می‌شود)، سپس جدول‌های نیمه‌کاره را پاک و نصب را از نو کامل می‌کند. کافی است `install.php` را دوباره باز کنید و «شروع نصب» را بزنید؛ به‌همراه آن حتماً `public/install-selfheal.php` نیز روی هاست باشد.
- **بعد از نصب، ریشه دامنه ۴۰۴ می‌دهد:** Wizard محل ریشه دامنه را تشخیص می‌دهد. اگر ریشه دامنه روی پوشه پروژه (و نه `public`) باشد، به‌صورت خودکار یک `.htaccess` در ریشه می‌سازد که همه درخواست‌ها را به `public` هدایت می‌کند. اگر دامنه به پوشه‌ای بالاتر از پروژه اشاره کند، یا محتوای `public` را مستقیماً در ریشه دامنه آپلود کنید یا در پنل هاست Document Root را روی پوشه `public` تنظیم کنید. اگر سرور nginx باشد (شناسایی خودکار)، باید در تنظیمات سرور درخواست‌ها به `public/index.php` هدایت شوند چون nginx فایل `.htaccess` را نمی‌خواند.

`public/install.php` فقط وقتی قفل نصب وجود نداشته باشد فعال است، فرم آن CSRF دارد، اتصال دیتابیس را پیش از نوشتن تنظیمات بررسی می‌کند و اطلاعات حساس را در HTML یا لاگ نمایش نمی‌دهد. این فایل را هرگز روی یک نصب فعال بدون قفل رها نکنید.

پس از نصب:

`storage/app/public` باید قابل نوشتن باشد. اگر هاست اجازه ساخت symlink ندهد، مسیر عمومی `/storage/...` از داخل Laravel سرو می‌شود و آپلود لوگو/تصاویر همچنان کار می‌کند؛ اجرای `storage:link` فقط برای سرو مستقیم و بهتر فایل‌ها توصیه می‌شود.

```bash
php artisan storage:link # در صورت پشتیبانی هاست
php artisan optimize:clear
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

`AdminUserSeeder` را فقط زمانی اجرا کنید که `SEED_ADMIN_PASSWORD` تنظیم شده و قصد ساخت حساب‌های اولیه را دارید. پس از ورود، رمز حساب‌ها را تغییر دهید و در صورت عدم نیاز، مقدار seed را از محیط Production حذف کنید.

## اپلیکیشن موبایل (PWA)

لوگوی سایت از بخش «لوگوی سایت» در صفحه تنظیمات سایت (`/admin/settings`) در `public/images/site-logo.*` ذخیره می‌شود تا هدر و فوتر روی هاست بدون symlink هم همیشه قابل نمایش باشند. لوگوی اپلیکیشن از بخش «لوگوی اپلیکیشن» در `storage/app/public/app-icons` ذخیره می‌شود و manifest و favicon به‌صورت پویا از مسیرهای `/app-manifest.webmanifest` و `/app-icon` همان تصویر را استفاده می‌کنند.

نسخه وب قابلیت نصب به‌صورت اپلیکیشن روی Android و iOS را دارد و نیازی به دیتابیس جداگانه ندارد. قبل از Build نهایی، در صورت استفاده از اعلان Push مقدار عمومی `VITE_VAPID_PUBLIC_KEY` را در `.env` قرار دهید؛ این کلید محرمانه نیست اما کلید خصوصی VAPID هرگز نباید در فرانت یا Git قرار بگیرد.

```bash
npm run build
```

کاربر در سایت دکمه «نصب اپلیکیشن» را می‌بیند. در iPhone، نصب از مسیر Share → Add to Home Screen انجام می‌شود. Service Worker فقط فایل‌های عمومی و assetها را cache می‌کند و پاسخ‌های `/dashboard`، `/admin` و `/api` را cache نمی‌کند. برای Push واقعی، HTTPS، VAPID و worker ارسال اعلان باید روی Production تنظیم شوند.

## مدیریت صفحات و متن‌های ثابت

در پنل ادمین از مسیر **محتوا و ویترین سایت → مدیریت صفحات سایت**، صفحات اصلی، دوره‌ها، خدمات، کوچینگ، درباره ما، تماس، بلاگ و فروشگاه به‌صورت جداگانه قابل انتخاب هستند. عنوان، متن معرفی، متن دکمه‌ها و آیکون سربرگ از همین بخش ذخیره می‌شوند و برای این قابلیت migration جدیدی لازم نیست؛ داده‌ها در جدول `settings` با گروه `pages` نگهداری می‌شوند.

محتوای رکوردی مانند عنوان و توضیحات هر خدمت، دوره، محصول یا مقاله از مسیر **استودیو محتوا** ویرایش می‌شود. پس از انتشار فایل‌های جدید، کش Laravel و route cache را پاک کنید و کل `public/build` جدید را روی هاست جایگزین کنید:

```bash
php artisan optimize:clear
php artisan config:cache
php artisan route:cache
php artisan view:cache
npm run build
```

در هاست بدون SSH، اجرای build باید روی سیستم توسعه انجام شود و کل پوشه `public/build` همراه فایل‌های PHP جدید آپلود شود.

## نظرسنجی‌های خصوصی و لینک کانال

از منوی **رشد و اتومارکتینگ → نظرسنجی‌های خصوصی** نظرسنجی را بسازید. این نظرسنجی در منوی عمومی سایت، صفحه اصلی و sitemap قرار نمی‌گیرد و فقط با لینک تصادفی قابل دسترسی است؛ نظرسنجی‌های پیش‌نویس یا بسته‌شده پاسخ عمومی نمی‌دهند.

در فرم نظرسنجی می‌توانید وضعیت (پیش‌نویس/فعال/بسته)، زمان شروع و پایان، تعداد سؤال‌های قبل از ثبت‌نام، نوار پیشرفت، ترتیب تصادفی، پاسخ مجدد، پیام خوش‌آمد و پایان، مسیر بعد از تکمیل و نوع سؤال را تنظیم کنید. سؤال‌های یک‌گزینه‌ای، چندگزینه‌ای، متنی، تشریحی، عددی، امتیازی و بله/خیر پشتیبانی می‌شوند.

برای سناریوی کانال، مقدار **تعداد سؤال قبل از ثبت‌نام** را مثلاً ۳ قرار دهید، نظرسنجی را فعال کنید، دکمه کپی لینک را بزنید و لینک را در کانال بفرستید. پاسخ‌های مرحله اول در session و دیتابیس ذخیره می‌شوند؛ بعد از ثبت‌نام، کاربر با ورود خودکار به همان نظرسنجی برمی‌گردد و سؤال‌های باقی‌مانده را می‌بیند. پاسخ‌ها از داخل فرم نظرسنجی قابل مشاهده و با دکمه **خروجی پاسخ‌ها** به CSV قابل دریافت هستند.

برای انتشار این قابلیت روی هاست، migrationهای جدید را اجرا کنید و کل `public/build` را جایگزین کنید:

```bash
php artisan migrate --force
php artisan db:seed --class=RoleAndPermissionSeeder --force
php artisan optimize:clear
php artisan config:cache
php artisan route:cache
npm run build
```

در هاست بدون SSH، migrationها را از Wizard نصب یا ابزار migration پنل اجرا کنید. migration مجوزهای نظرسنجی را برای نقش‌های `admin` و `editor` نیز اضافه می‌کند؛ پاسخ‌ها شامل اطلاعات حساب کاربر هستند، پس لینک CSV را عمومی نکنید.

## Queue، Cron و Cache

Worker صف باید با Supervisor یا سرویس مدیریت پردازش اجرا شود:

```bash
php artisan queue:work redis --sleep=2 --tries=3 --timeout=90
```

Cron هر دقیقه:

```cron
* * * * * cd /path/to/project && php artisan schedule:run >> /dev/null 2>&1
```

پس از هر انتشار:

```bash
php artisan optimize:clear
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

### مانیتورینگ سلامت اتصال سرویس‌ها

دو کامند برای بررسی اتصال پنل‌های پیامک و درگاه‌های پرداخت (بدون ارسال پیام یا ایجاد تراکنش) وجود دارد؛ می‌توانید آن‌ها را به‌صورت دوره‌ای در Cron اجرا کنید و در صورت خطا اعلان بگیرید:

```cron
# هر ۳۰ دقیقه؛ در صورت خطا کد خروجی ۱ برمی‌گردد و متن خطا به لاگ نوشته می‌شود
*/30 * * * * cd /path/to/project && php artisan sms:check-connection --json >> /var/log/sms-health.log 2>&1 || echo "SMS panel check failed" >> /var/log/sms-health.log
*/30 * * * * cd /path/to/project && php artisan payment:check-connection --json >> /var/log/payment-health.log 2>&1 || echo "Payment gateway check failed" >> /var/log/payment-health.log
```

`--json` خروجی ساختاریافته برای مانیتورینگ می‌دهد و `--strict` باعث می‌شود پنل/درگاهی که هنوز کلید ندارد هم به‌عنوان خطا گزارش شود.

### اتومارکتینگ زمان‌بندی‌شده

کمپین‌های دستی با «زمان اجرای یک‌باره» از پنل به‌صورت خودکار توسط دستور زیر dispatch می‌شوند. اجرای `schedule:run` هر دقیقه و worker صف برای ارسال واقعی ضروری است:

```bash
php artisan marketing:dispatch-scheduled
php artisan commerce:release-expired-reservations
php artisan marketing:winback-visitors
php artisan crm:dispatch-inactive-campaigns
php artisan crm:remind-stale-leads
php artisan surveys:publish-eitaa-scheduled
php artisan surveys:send-eitaa-summaries
php artisan queue:work redis --sleep=2 --tries=3 --timeout=120
```

`surveys:publish-eitaa-scheduled` هر دقیقه اجرا می‌شود و نظرسنجی‌هایی که برایشان «زمان‌بندی انتشار خودکار در ایتا» تنظیم شده و زمانشان رسیده است را در کانال ایتا منتشر می‌کند (هر نظرسنجی فقط یک‌بار). برای استفاده از این قابلیت، Cron هاست باید فعال باشد و توکن ربات + شناسه کانال ایتا در تنظیمات سایت ذخیره شده باشد.

`surveys:send-eitaa-summaries` هر ۵ دقیقه اجرا می‌شود و برای نظرسنجی‌های بسته‌شده (وضعیت «بسته‌شده» یا پایان‌یافتن تاریخ پایان) که پاسخ دارند، جمع‌بندی نتایج را در کانال ایتا منتشر می‌کند. هر نظرسنجی فقط یک‌بار جمع‌بندی می‌گیرد؛ از پنل هم می‌توان جمع‌بندی را دستی ارسال کرد.

قالب جمع‌بندی از پنل هر نظرسنجی قابل تنظیم است: «متن قبل از نتایج»، «متن بعد از نتایج» (با متغیر `{title}`) و انتخاب اینکه کدام سؤال‌ها در جمع‌بندی نمایش داده شوند (تیک «نمایش در جمع‌بندی» بالای هر سؤال).

جمع‌بندی پیش‌فرض به‌صورت **کارت گرافیکی PNG با رنگ‌بندی برند** تولید و ارسال می‌شود (توزیع پاسخ‌های هر سؤال با درصد، میانگین امتیازها). این کارت با پسوند GD و فونت وزیرمتن ساخته می‌شود؛ اگر سرور افزونه GD نداشته باشد یا فونت موجود نباشد، خودکار به پیام متنی ساده برمی‌گردد. با گزینه «جمع‌بندی به‌صورت تصویر» در تنظیمات ایتا می‌توان همیشه فقط متن ارسال کرد. الزامات هاست:

- افزونه GD با پشتیبانی FreeType (`php -m` باید `gd` را نشان دهد؛ در اکثر هاست‌های cPanel فعال است)
- آپلود پوشه `resources/fonts/` (فونت‌های وزیرمتن با لایسنس OFL همراه پروژه هستند)

`marketing:winback-visitors` هر شب اجرا می‌شود و کاربرانی را که چند صفحه از سایت (دوره/فروشگاه/خدمات/بلاگ) را دیده‌اند اما خریدی نداشته‌اند با پیامک و اعلان داخل پنل پیگیری می‌کند؛ متن پیام‌ها و بازه بررسی از صفحه «اتصالات و پیگیری خودکار» پنل ادمین (`/admin/settings/automations`، بخش «پیگیری بازدیدکنندگان») کنترل می‌شود و کلید `winback_enabled` باید فعال باشد.

`crm:dispatch-inactive-campaigns` هر روز ساعت ۹ صبح کمپین‌های فعال با تریگر «کاربر غیرفعال» را اجرا می‌کند؛ هر کاربر فقط یک‌بار در بازه تعیین‌شده (`cooldown_days`، پیش‌فرض ۱۴ روز) همان کمپین را دریافت می‌کند و تاریخچه هر ارسال در جدول `marketing_campaign_recipients` ثبت می‌شود.

`crm:remind-stale-leads` هر روز ساعت ۱۰ صبح لیدهایی را که پس از آخرین فعالیت به‌مدت تعیین‌شده (پیش‌فرض ۷ روز) بی‌پاسخ مانده‌اند با پیامک یادآوری می‌کند؛ بازه بی‌پاسخی، فاصله بین دو یادآوری و متن پیامک از صفحه «اتصالات و پیگیری خودکار» پنل ادمین (`/admin/settings/automations`، بخش «پیگیری لیدهای بی‌پاسخ») کنترل می‌شود و کلید `lead_reminder_enabled` باید فعال باشد. هر یادآوری در تاریخچه فعالیت‌های لید (نوع `reminder`) ثبت می‌شود.

کمپین‌های رویدادمحور برای ثبت لید و خرید دوره از داخل برنامه وارد صف می‌شوند. ثبت‌نام در سایت و تکمیل فرم تماس، خودکار لید می‌سازند و رویداد «ثبت لید جدید» را فعال می‌کنند. رضایت‌های پیامک، ایمیل و اعلان در جدول `marketing_consents` ذخیره و گیرنده‌های لغوشده از کمپین حذف می‌شوند. در محیط Production ابتدا درایور پیامک را روی Sandbox یا Log تست کنید و سپس کلید واقعی را فعال کنید.

### رزرو موجودی

سفارش‌های محصولات فیزیکی هنگام Checkout تا زمان `reservation_expires_at` موجودی را رزرو می‌کنند. دستور `commerce:release-expired-reservations` باید هر پنج دقیقه اجرا شود تا سفارش‌های رهاشده موجودی را آزاد کنند.

## داده‌های محلی که نباید Deploy شوند

- `.env` و هر فایل شامل کلید API یا رمز.
- `.freebuff/preview.sqlite`، لاگ Preview و دیتابیس‌های Desktop.
- `storage/inertia-devtools` که فقط برای بررسی محلی است.
- `node_modules` و `vendor` در صورت نصب جداگانه روی سرور.
- فایل‌های private دیجیتال را داخل `public/storage` یا ریشه public قرار ندهید.

این مسیرها در `.gitignore` محافظت شده‌اند.

## بررسی بعد از انتشار

1. صفحه اصلی، `/courses`، `/services`، `/blog` و `/shop` با دامنه واقعی باز شوند.
2. در Network هیچ درخواست localhost، پورت Preview یا منبع Unsplash برای Hero وجود نداشته باشد.
3. ورود OTP، بازیابی رمز، محدودکننده درخواست و خروج بررسی شوند.
4. یک سفارش رایگان و یک تراکنش Sandbox بررسی شود؛ سپس درگاه Production فعال شود.
5. تغییر لوگو، تنظیمات SEO، پاپ‌آپ، آمار صفحه اصلی و ایستگاه‌های مسیر از پنل ادمین بررسی شوند.
6. ارسال پیامک تست فقط به شماره کنترل‌شده انجام شود.
7. لاگ‌های Laravel، صف‌ها، فضای دیسک و بکاپ دیتابیس پایش شوند.
8. صفحه Course Player، ثبت پیشرفت درس، فاکتور قابل چاپ و رزرو زمان کوچینگ بررسی شوند.
9. Push Subscription فقط پس از تنظیم VAPID/Web Push Provider فعال شود؛ Service Worker به‌تنهایی ارسال Push انجام نمی‌دهد.
10. HTTPS، کوکی Secure، دامنه Session و مجوز نوشتن `storage` و `bootstrap/cache` بررسی شوند.

## گزارش ممیزی امنیت و کیفیت محلی

این ممیزی در محیط توسعه و فقط روی همین پروژه انجام شد و شامل اسکن تهاجمی یا تست روی هاست عمومی نیست.

- `php artisan test`: **۱۳۲ تست موفق، ۹۶۹ assertion موفق** (۱ تست XLSX به‌دلیل نبودن ZipArchive روی محیط فعلی skip شد).
- `npm run build`: موفق؛ رگرسیون ظاهری صفحات عمومی در دو تم، دسکتاپ/موبایل/تبلت: **۳۶ تست موفق**.
- `npm audit --omit=dev --audit-level=high`: بدون آسیب‌پذیری با سطح high یا critical.
- `php composer.phar audit --no-dev`: بدون advisory امنیتی.
- `npm run build` و lint تمام فایل‌های PHP: موفق.
- سناریوهای غیرمخرب شامل کنترل دسترسی نقش‌ها، جلوگیری از IDOR سفارش، محدودیت OTP، عدم افشای وجود حساب، اعتبارسنجی پرداخت و هدرهای امنیتی بررسی شدند.
- callback پرداخت به همان شناسه تراکنش ساخته‌شده برای سفارش متصل شد و callback تکراری با قفل دیتابیس idempotent است.
- هدرهای `nosniff`، `SAMEORIGIN`، سیاست ارجاع و Permissions Policy به پاسخ‌های وب اضافه شده‌اند.
- آپلود لوگو به فرمت‌های تصویری raster محدود است؛ SVG عمومی برای کاهش ریسک XSS پذیرفته نمی‌شود.
- نمودارهای داشبورد ادمین از ۶۰ کوئری روزانه به دو کوئری تجمیعی کاهش یافتند.

مواردی که برای قبل از انتشار واقعی هنوز باید انجام شوند:

1. اجرای `composer audit` و `npm audit` روی سرور پس از هر deploy و به‌روزرسانی lockfileها.
2. اسکن DAST مجاز روی دامنه staging با ابزارهایی مانند OWASP ZAP؛ این کار روی localhost انجام نشد چون اسکن شبکه‌ای تهاجمی نیست و باید با اجازه و محیط جداگانه انجام شود.
3. تست نفوذ دستی توسط متخصص مستقل، مخصوصاً روی نقش‌ها، فایل‌های خصوصی، webhook درگاه و پنل ادمین.
4. تنظیم `APP_ENV=production`، `APP_DEBUG=false`، HTTPS، کوکی Secure و Redis در سرور واقعی.
5. تعریف backup رمزنگاری‌شده، مانیتورینگ خطا، alert برای پرداخت‌های ناموفق و محدودیت نرخ بر اساس IP به‌عنوان لایه تکمیلی OTP.
6. تکمیل تست تراکنش Sandbox هر درگاه با callback واقعی؛ تست محلی جایگزین تست بانکی نیست.
